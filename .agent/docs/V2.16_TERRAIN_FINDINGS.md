# V2.16 — Terrain Findings and Resolved Defects

## Scope

This document records empirical defects discovered while copying the V2.16 `.agent` bundle into isolated projects and then replaying the workflow on a realistic codebase.

It distinguishes terrain evidence from CI coverage. It does not mark the PR ready for merge and does not replace the remaining host-visible MCP gate.

## Real Graphify schema

The installed Graphify build completed with two nodes and one relation. Its `graph.json` used NetworkX node-link data with root fields:

```text
directed
multigraph
graph
nodes
links
hyperedges
```

The original readiness fixture assumed only `nodes + edges`; terrain therefore exposed a false `GRAPHIFY_CORRUPT` verdict after a successful build.

The readiness adapter now accepts only explicit supported edge collections:

```text
nodes + edges
nodes + links
```

It rejects absent collections, non-list collections and contradictory dual collections. `GRAPHIFY_READY.json` records the bound edge field.

## Two-terminal stale-workspace replay — 2026-07-17

Two real OpenCode terminals started from the same copied bundle after product
sources changed. Both detected `GRAPHIFY_STALE_WORKSPACE`, but they diverged:

- one terminal tried the standalone SCRIBE build, which the autonomous bash
  policy correctly denied, then stopped and asked the user to intervene;
- the other terminal manually called `graphify_project_build` twice with
  different bounds before rerunning INIT and eventually reaching
  `TENOR_INIT_READY`.

This is terrain proof that the previous workflow was not stable: correctness
depended on the small model choosing the right recovery surface. The resolved
contract moves bounded recovery inside canonical TENOR INIT. The init lock now
covers the build, concurrent waiters recheck readiness, the MCP maintenance
tool uses the same idempotent single-flight engine, and any workspace change
during the build invalidates `GRAPHIFY_READY.json` instead of accepting a stale
snapshot. Terrain confirmation on the post-fix head remains required before
merge.

## Concurrency defects exposed by expanded validation

### Partial TENOR lock creation

A waiter could read a lock while its owner was still writing JSON. An empty parse was interpreted as epoch zero, making a fresh lock appear stale. Age now falls back to the lock file `mtime`, while stale removal still rechecks ownership before unlinking.

### Windows manifest temporary-file collision

Concurrent writers could generate the same timestamp-derived temporary name. Manifest writes now use an exclusively created `tempfile.mkstemp()` file in the destination directory before `fsync` and atomic replacement.

### Host-instruction temporary-file collision

The host auto-repair writer still used `time.time_ns()` for `AGENTS.md` temporaries after the manifest writer had been hardened. It now also uses `tempfile.mkstemp()` and preserves atomic replacement. A concurrent test runs 64 repairs through 16 workers and requires one managed block with no temporary residue.

### Destructive Windows PID probe

`os.kill(pid, 0)` is not a POSIX-style existence probe on Windows. TENOR now uses read-only `OpenProcess` and `GetExitCodeProcess`, closes every handle and treats access denial as an existing but uninspectable owner.

### In-process finalization transaction

Concurrent finalizers could write `ready` and then observe another write between the write and gate inspection. Finalization now protects write plus inspection with a reentrant in-process transaction lock; the TENOR file lock remains the inter-process authority.

## Smoke fixture isolation

A Graphify smoke fixture once survived `mcp_smoke` and was then correctly rejected by the following red-team as `GRAPHIFY_FIXTURE_FORBIDDEN`.

Fixture lifecycle is now scoped:

1. snapshot prior canonical Graphify output;
2. install and authorize one fixture;
3. execute exactly one smoke subprocess;
4. restore prior output byte-for-byte or restore absence;
5. restore the previous environment even when the smoke fails.

Diagnostic logs live outside the checkout so Git hygiene remains strict.

## Raw-copy replay on `algowebsite` — host-binding defects

A later raw copy of the complete current `.agent/` into `algowebsite` proved that relocation and stale-Graphify refusal worked, but exposed four defects after local recovery:

1. the printed fallback used bare `python` on a POSIX machine where only `python3` existed;
2. TENOR did not mechanically detect/configure the actual project-local host;
3. the full proof bearer token appeared in terminal output and a manually piped JSON-RPC call;
4. a shell-launched MCP server could be presented in prose as `TENOR_INIT_READY` even though OpenCode had not exposed the tools.

The corrected contract now returns interpreter argv, manages only verified project-local OpenCode/Claude/Codex configuration, records a config-hash binding receipt, requires restart/reconnect after changes, rejects an ordinary shell process as `HOST_MCP_UNBOUND`, and consumes a server-side one-time proof without printing or persisting the full token. The internal `TENOR_INIT_BRIDGE_OK` receipt is promoted by the public wrapper to terminal `TENOR_INIT_READY` only after host-process, root and session proofs all pass.

Executable regression coverage now includes complete raw copy, destination memory present/absent, stale graph refusal, ambiguous host refusal, OpenCode JSONC preservation/idempotence, shell bridge rejection, current-interpreter actions, six concurrent proof issuers and single-use consumption. These are code/test proofs; the final OpenCode root-binding, micro-write and six-terminal terrain replays remain mandatory before merge.

## Real OpenCode TENOR TASK replay — governance bypasses

The first real host-bound task produced new evidence that invalidated the
earlier CI closure claim:

- descriptive prose was persisted as `intent`, then compared literally by the
  write gate, producing repeated `TASK_CONTEXT_INTENT_MISMATCH`;
- the model retired identities and registered replacements to escape HARD_STOP;
- one logical task created several active task contexts;
- three native OpenCode edits changed product files with zero MCP patch receipt;
- a `FIXED` SCRIBE record was staged without an applied MCP patch;
- the model ran global `graphify update .`, creating root `graphify-out/` and
  dirtying tracked/generated product paths;
- `test_multi_agent_resource_lock.py` was absent from CI and, when invoked
  directly, had no `unittest.main()`. Its old fixture was stopped by the TENOR
  installation gate before it could measure lock atomicity.

The corrected source uses a strict `read|write|delete` intent enum, one active
task per identity, retirement blockers, host-bound registration authority,
receipt-bound bugfix records, sequential multi-file rescoping and OpenCode
`edit/bash=deny`. Graphify now builds in an isolated mirror and is published
only to `.agent/state/outputs/graphify-out/`; a bound host uses
`graphify_project_build`.

The repaired resource-lock suite executes 23 real tests, including repeated
two-agent races. This proves lock atomicity; it does not yet replace the final
six-terminal `algowebsite` replay. PR nº 1 remains Draft and merge into `v2`
remains forbidden.

## Compact public task API — implementation evidence, terrain still required

The later OpenCode replay proved that exposing the fine-grained protocol to a
small model remained operationally unstable even after individual gates were
correct: one product fix consumed dozens of calls, repeatedly mismatched
intent/resource context, created replacement tasks/agents and finally bypassed

The source now advertises four normal task tools. `tenor_task_start` performs

`tenor_apply_changeset` owns multi-file path/scope/hash/lock preflight,

presence/current/last/next state. `tenor_task_control` is owner-only.

Local executable coverage proves normal two-file commit, stale-hash zero-write,
validator rollback, injected mid-commit rollback, idempotent retry, request-id
conflict, create/confirmed-delete, traversal/symlink refusal, process-bound
identity, two-agent ownership isolation, live/dead PID handling and rolling
task TTL. These remain code/test proofs. A new real OpenCode atomic commit,
rollback and six-terminal replay is still mandatory before merge into `v2`.

## Destructive `replace` replay — source-level root cause and correction

A subsequent real OpenCode task produced the most severe write-path evidence:
the model passed a five-line snippet to `tenor_apply_changeset` with
`operation="replace"`. The runtime interpreted `content` as the complete file
and atomically truncated a healthy 2,051-line `useDrawingManager.ts` to five
lines. After the human restored the file from Git, unified-diff context retries
continued to fail, the stale task could not finish without a changeset, and the
model asked the human to apply a manual patch containing an additional scope
error (`dr` referenced outside its `map`).

The corrected contract is mechanical rather than advisory:

- normal text changes use one `edit` operation per path with one or more exact
  `old_text/new_text/expected_occurrences` edits;
- missing or ambiguous anchors fail before the first write;
- destructive full-file shrink is rejected unless path, base hash and new hash
  are confirmed together;
- `create` no longer requires the model to know the private `__new_file__`
  sentinel;
- every mutation requires at least one validator;
- validator completion rechecks every target hash and rolls back target drift;
- direct-write auditing falls back to a filesystem snapshot outside Git and
  blocks closure when a validator or tool mutates an unscoped file;
- no-op changesets cannot close tasks;
- a failed uncommitted task can be cancelled without a patch;
- a stale SCRIBE/Graphify capsule refreshes inside the same task id;
- every completed task receives a persisted memory-admission verdict and
  durable source fixes are promoted into canonical SCRIBE automatically;
- manual patch fallback is explicitly forbidden.

Executable regression coverage reproduces the exact 2,051-to-5-line failure,
proves zero-write rejection, structured multi-edit atomicity, anchor mismatch
rejection, hash-bound full-replacement confirmation, mandatory validators,
decision-capsule drift/refresh and canonical-memory admission. This is code
evidence; the corrected raw-copy OpenCode replay remains required before merge.

## Repeated one-shot MCP SQLite corruption — root cause and policy correction

Repeated mutating one-shot MCP processes exposed a failure that server-start
tests did not: 100 consecutive `--list-tools` processes preserved integrity,
but a normal resource-lock workflow corrupted `coordination.sqlite` on its
fourth replay. `PRAGMA integrity_check` reported out-of-order rowids and unused
pages even after all WAL sidecars had disappeared. Both `db.py` and
`patch_queue.py` independently forced WAL, while the portable bundle can run on
filesystems whose shared-memory or locking behavior has not been qualified.

The runtime now has one connection-policy authority. It defaults to SQLite
rollback journal `DELETE`, `synchronous=FULL`, foreign keys, application-id
verification and a bounded 30-second busy timeout. `patch_queue` delegates to
that same authority. WAL is available only through the explicit operator opt-in
`AGENT_SQLITE_JOURNAL_MODE=WAL`; invalid values and effective-mode mismatches
fail closed.

Post-correction local evidence on 2026-07-19:

```text
connection-policy and reset tests: 20/20 passed
cross-process stress: 16 writers x 64 rows = 1,024/1,024 committed
repeated complete MCP smoke runs: 10/10 passed
integrity_check after every smoke: ok
integrity_check after cross-process stress: ok
effective default journal mode: delete
```

This closes the reproduced local corruption mechanism. It does not replace the
remaining raw-copy OpenCode and six-terminal terrain replay on the final commit.

## OpenCode MCP request timeouts — head-of-line root cause and bounded jobs

On 2026-07-21, a real OpenCode implementation session reported four consecutive
`-32001 Request timed out` failures for `file_hash`,
`tenor_apply_changeset`, `tenor_activity` and `portability_check`. The host had
no native write/edit fallback, so mutation capacity fell to zero after a
successful TENOR INIT.

The local replay isolated a transport-level cause: MCP stdio dispatch was
sequential and `tenor_apply_changeset` executed up to twelve 600-second
validators inline. A synthetic two-second tool followed immediately by
`file_hash` produced no response during the first 500 ms; both responses arrived
after 2,093 ms. `graphify_project_build` had the same inline risk with a
3,600-second bound. The configured OpenCode MCP timeout could not make those
operations safe because the server itself held the request loop.

The corrected runtime now:

- returns durable, non-terminal `TENOR_CHANGESET_ACCEPTED` and
  `GRAPHIFY_BUILD_ACCEPTED` receipts;
- executes changesets and Graphify builds in isolated bounded workers;
- exposes redacted job state/results through `tenor_activity` and
  `graphify_required_check`;
- rejects task control while a task job is active;
- enforces idempotent request fingerprints and a cross-process worker ceiling;
- bounds stdout/stderr memory and kills validator/Graphify descendant process
  groups on timeout;
- uses a worker watchdog, three finite recovery attempts and explicit
  `TENOR_JOB_RETRY_EXHAUSTED` terminal state;
- keeps payloads out of public snapshots and clears them at terminal state.

Local executable evidence on 2026-07-21:

```text
public TENOR API: 14/14 passed, including a 2-second validator while
  file_hash + tenor_activity + portability_check remained responsive
durable jobs: 6/6 passed, including watchdog cutoff and retry exhaustion
transaction/validator safety: 20/20 passed
V2.16 terrain enforcement: 17/17 passed
public performance: 9/9 passed
cold file_hash p95: 108.3 ms
64 concurrent cold file_hash p95: 293.3 ms
500 durable submissions p95: 4.2 ms
warm graphify_required_check p95: 3.4 ms
warm portability_check p95: 1.8 ms
1000 in-process file hashes: 0.00 MB retained, 1.01 MB traced peak
```

These results close the reproduced local head-of-line mechanism. They do not
yet prove the final raw-copy OpenCode host replay, long-duration endurance on
Linux/macOS/Windows, or six simultaneous real host terminals; those remain
release gates rather than inferred successes.

### Same-namespace direct-write red-team

A second Codex task applied one declared source edit while its first validator
successfully appended an undeclared marker to `README.md`. Both validators
returned zero. TENOR itself detected the bypass before commit:

```text
DIRECT_WRITE_BYPASS_DETECTED
TENOR_CHANGESET_UNAUTHORIZED_MUTATION_ROLLED_BACK
transaction status: rolled_back
restored: src/sample/simple.py
```

Independent hashes proved that the declared source returned to its exact
baseline, canonical SCRIBE remained unchanged, and the external README evidence
was preserved rather than silently erased. The blocked task was then cancelled
and left zero active jobs.

The tripwire remains detection rather than an OS write barrier. A write made
from another isolated sandbox namespace can be invisible to the MCP process
until namespaces merge. Preventing such cross-sandbox concurrent writes
requires host/OS isolation and is not claimed by this runtime transaction.

### Release-candidate corrections from this replay

- Codex project config includes server-scoped
  `default_tools_approval_mode = "approve"` for non-interactive MCP calls.
- durable worker logs and owned smoke workspaces are ignored by Git;
- canonical promotion validates the same doctor contract before replacement;
- the direct-filesystem guard runs while declared-file backups still exist and
  rolls them back on bypass;
- generated Graphify guidance matches autonomous TENOR INIT and does not dirty
  an existing bundle document.

This replay closes the raw-copy Codex micro-write, SCRIBE persistence, Graphify
restart and same-namespace rollback gates. It does not prove multi-day endurance,
macOS/Windows terrain, or six simultaneous real host terminals.
